# Лабораторная работа №5. Архитектурные стили и протоколы взаимодействия Web-API

## Цель работы

1. Освоить один из альтернативных архитектурных стилей Web-API, отличных от REST (GraphQL, WebSockets, WebHooks, SOAP и др.).
2. Научиться выбирать архитектурный стиль под конкретную задачу и аргументировать свой выбор.
3. Расширить функциональность существующего сервиса, интегрируя новый тип API вместе с уже реализованным REST API.
4. Закрепить навыки проектирования и реализации backend-приложений на Node.js + Express в более «приближенном к продакшену» сценарии.

## Шаг 1. Анализ архитектурных стилей API

1. Особенности GraphQL
* Клиент сам выбирает нужные поля, один endpoint, нет лишних данных.
2. Когда использовать WebSockets
* Когда нужно общение в реальном времени: чат, уведомления, онлайн-обновления.
3. Для чего нужны WebHooks
* Для отправки уведомлений на внешний URL при событии (создание, обновление и т.д.).
4. Где используется SOAP
* В старых корпоративных и государственных системах, где требуется строгий формат XML.

## Шаг 2. Выбор типа Web-API и обоснование

Я выбрала архитектурный стиль WebHooks, так как он лучше всего дополняет существующий REST API моего ToDo-приложения.

1. Какую проблему или ограничение текущего REST-подхода я решаю с помощью WebHooks?
* REST не умеет автоматически уведомлять внешние сервисы о событиях.
Клиент должен сам постоянно спрашивать сервер («polling»), что создаёт лишнюю нагрузку.
WebHooks позволяют серверу самому отправлять уведомления, когда событие уже произошло.

2. Какие преимущества даёт WebHooks моему приложению?
* Todo-приложение генерирует много событий (создание, обновление, удаление задач).
* WebHooks позволяют отправлять их во внешние сервисы без изменений фронтенда.
* Легко интегрируется в текущую архитектуру на Express + Prisma.

3. Как WebHooks поможет улучшить производительность, взаимодействие клиентов или удобство разработки?
* Уменьшают нагрузку на сервер (нет опросов каждые X секунд).
* Улучшают взаимодействие с внешними сервисами - они сразу получают событие.

## Шаг 4. Проектирование новой функциональности

1. Сценарий работы WebHook

- В моём приложении сервер выступает как отправитель WebHook.
При каждом важном событии (создание, обновление, переключение статуса или удаление задачи) сервер автоматически отправляет HTTP-запрос на заранее зарегистрированный внешний URL.
Таким образом внешние сервисы могут получать уведомления в реальном времени без изменения клиентской части.

2. Реализованная функциональность
2.1. Регистрация WebHook URL

Создан отдельный маршрут:

POST /webhooks/register


Он принимает JSON вида:

```js
    { "url": "https://example.com/hook" }
```
URL сохраняется в локальном списке зарегистрированных WebHooks.

2.2. Автоматическая отправка WebHooks на события

WebHook отправляется при следующих действиях над задачами:

* создание задачи (todo_created)
* обновление задачи (todo_updated)
* переключение статуса (todo_toggled)
* удаление (todo_deleted)

Каждое событие вызывает функцию:
```js
    sendWebhook(eventName, eventData);
```
Она отправляет POST-запросы на все зарегистрированные WebHook URL.

## Шаг 5. Реализация WebHook

5.1. Добавление необходимых зависимостей

Для отправки WebHook-запросов используется библиотека axios:

```js
    npm install axios
```

5.2. Добавление маршрута для регистрации WebHook

Создан endpoint:

```js
    POST /webhooks/register
```
Он позволяет клиенту отправить URL, на который сервер будет отправлять уведомления.

```js
    router.post("/register", (req, res) => {
    const { url } = req.body;
    registerWebhook(url);

    res.json({
        message: "WebHook успешно зарегистрирован",
        url,
    });
    });
```
5.3. Реализация WebHook-сервиса

Сервис отвечает за хранение зарегистрированных URL и отправку событий.
```js
    const registeredWebhooks = [];

    export const registerWebhook = (url) => {
    registeredWebhooks.push(url);
    };

    export const sendWebhook = async (event, data) => {
    for (const url of registeredWebhooks) {
        await axios.post(url, {
        event,
        data,
        timestamp: new Date().toISOString()
        });
    }
    };
```
5.4. Интеграция WebHooks в существующую бизнес-логику

WebHooks были встроены в контроллер задач (todoController), и теперь отправляются автоматически при ключевых событиях:

* Создание задачи
```js
    sendWebhook("todo_created", todo);
```
* Обновление задачи
```js
    sendWebhook("todo_updated", updatedTodo);
```
* Переключение статуса
```js
    sendWebhook("todo_toggled", updatedTodo);
```
* Удаление задачи
```js
    sendWebhook("todo_deleted", { id });
```
